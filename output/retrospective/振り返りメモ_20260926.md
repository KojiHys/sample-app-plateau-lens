# PLATEAU Lens AWSデプロイ 振り返りメモ

| 項目 | 内容 |
|---|---|
| 振り返り日 | 2026-09-26 |
| 対象 | PLATEAU Lensのdev環境デプロイと実環境検証 |
| 最終状態 | `us-east-1`で稼働。フォールバックとCognito Managed Loginを有効化済み |

## 1. 到達点

- S3 + CloudFront OAC、Cognito、HTTP API、Lambda、DynamoDB、BudgetをCDKでデプロイした。
- PLATEAU表示、SPA routing、S3直接アクセス拒否、CloudFront OAC、CORS、未認証POSTの401を実環境で確認した。
- フォールバックタイル635ファイルを専用S3へ同期し、CloudFront経由でroot tileset、child JSON、B3DMを取得できることを確認した。
- Cognito Managed Loginで2名が初回ログインを完了した。
- 保存ビューの作成、所有者別一覧、未ログイン公開共有を実環境で確認した。
- 別所有者DELETEの403と、実障害を起こした自動フォールバック切り替えは、デモに必須ではないため保留した。

## 2. 発生した事象と対応

| 段階 | 事象 | 原因 | 対応 |
|---|---|---|---|
| 初回deploy | API Gateway Stage作成失敗 | `RouteSettings`のmap値がCDKのstruct変換を通らず、lower camel caseのキーがCloudFormationへ出力された | `ThrottlingBurstLimit`と`ThrottlingRateLimit`をCloudFormation表記で設定し、合成templateを完全一致で検証した |
| 2回目deploy | Stageが対象Routeを見つけられず失敗 | Route keyは単なる文字列であり、StageからRouteへのCloudFormation依存関係が作られていなかった | StageをPOST/DELETE Routeへ明示的に依存させた |
| 2回目rollback | Web S3 bucketが空にならず`ROLLBACK_FAILED` | Web資産配布がStageと並列に進み、失敗前にS3へオブジェクトを投入した。rollback時のcustom resource削除だけでは空化できなかった | 承認後に生成物だけを削除してstackを復旧し、Web配布をStage成功後に実行する依存関係を追加した |
| ログイン確認 | `Login pages unavailable` | Managed Login v2 domainを作成しても、API/CDKで作成したapp clientにはbranding styleが自動作成されない | `AWS::Cognito::ManagedLoginBranding`を追加し、Cognito標準styleをclientへ関連付けた |
| フォールバック同期 | manifestとS3のbyte数が一致しない | manifestは取得時の受信量、S3は参照を相対URLへ書き換えた後の最終ファイルサイズを表していた | file数だけでなく、ローカル最終ファイルとS3 objectの合計byte数を比較した |

## 3. Lesson Learned

### 3.1 `cdk synth`成功はCloudFormation受理の証明ではない

CDK assertionは、期待値を誤って定義すると無効なtemplateを正しいものとして検証してしまう。特にL1 constructの`any` mapは、CDKのTypeScript用lower camel caseからCloudFormation用PascalCaseへ自動変換されない場合がある。

今後は次を行う。

- L1の`any` mapを使う箇所は、合成後templateの実際のキーを検証する。
- CloudFormation resource schemaに対するlintをCIへ追加する。
- unit testだけでなく、短命なdev stackでcreate/updateのsmoke testを行う。

### 3.2 文字列による参照はCloudFormation依存関係を作らない

`RouteSettings`内の`POST /views`はRouteのlogical IDや`Ref`ではない。値が一致していてもCloudFormationはStageとRouteを並列作成できる。

今後は次を行う。

- 作成順が必要なresourceは`Ref`の有無だけで判断せず、合成templateの`DependsOn`を確認する。
- CDK testではresourceの存在だけでなく、依存先のlogical IDをresource propertyから導出して検証する。
- deploy時に順序競合が起きる可能性があるcustom resourceも依存関係へ含める。

### 3.3 Custom Resourceの副作用はrollbackで完全に戻るとは限らない

`BucketDeployment`とS3 object自動削除は別々のLambda custom resourceである。CloudFormation stackがrollbackしても、途中で投入したオブジェクトが残り、bucket削除が失敗することがある。

今後は次を行う。

- Web資産配布を、API・認証など主要resourceの作成成功後に開始する。
- 失敗時はstack eventと残存resourceを読み取り確認し、対象データを特定してから削除承認を得る。
- `cdk destroy`やbucket空化を自動的に再試行しない。

### 3.4 Managed Login v2にはapp clientごとのbranding styleが必要

`ManagedLoginVersion=2`はdomainのbranding versionを選ぶ設定であり、programmaticに作成したapp clientのstyleまでは作成しない。Cognito consoleが暗黙に作るdefault styleを、CDKでは明示的に定義する必要がある。

今後は次を行う。

- Managed Login v2では`AWS::Cognito::ManagedLoginBranding`をapp clientごとに作成する。
- default styleを使う場合は`UseCognitoProvidedValues=true`とし、`Assets`と`Settings`を同時指定しない。
- domain、client、branding、Web配布の依存順をtemplateで確認する。
- login redirectだけで完了扱いにせず、email/password formが実際に描画されるところまでsmoke testする。

### 3.5 Profileのdefault regionとstackのtarget regionを分けて確認する

AWS profileのdefault regionを変更しても、CDK appが`env.region`を固定していればdeploy先は変わらない。

今後は次を行う。

- profile、`CDK_DEFAULT_REGION`、CDK stackの`env.region`を別々に確認する。
- synth後の`manifest.json`にある`aws://<account>/<region>`をdeploy前の最終判定に使う。
- deploy直前にSTS identityとCloudFormation stackのregionを再確認する。

### 3.6 配布設定はbuild時注入よりruntime configが扱いやすい

CloudFront URL、API endpoint、Cognito domain、client IDはdeploy時に決まる。Web assetを一度buildし、CDKが`runtime-config.json`を生成して配布する方式により、環境固有値をsourceやVite buildへ埋め込まずに済んだ。

今後も次を維持する。

- credentialや通知先をrepositoryへ保存しない。
- runtime config更新時はCloudFront invalidationと実配信値を確認する。
- `DEV_ORIGIN`未指定時はlocalhostをCORSとcallbackへ追加しない。

### 3.7 フォールバックは順序を守って有効化する

フォールバックURLを先に公開すると、障害時に存在しないtilesetへ切り替わる。今回は次の順序が有効だった。

1. フォールバック無効で初回deployする。
2. 専用S3へ同期する。
3. S3のfile数・byte数・root objectを確認する。
4. CloudFrontの`/tiles/*`をinvalidationする。
5. CloudFrontからroot、child、B3DMを取得する。
6. フォールバックURLを有効化して再deployする。
7. runtime configと`cdk diff`を確認する。

### 3.8 承認ゲートを操作単位に分けると失敗時の影響を限定できる

bootstrap、初回deploy、rollback stack削除、S3生成物削除、タイル同期、invalidation、Cognito user作成、branding更新を別々に承認した。各操作の直前にAccount、region、role、resource名、現在状態を再確認したことで、失敗時も対象外resourceを変更せずに復旧できた。

今後も次を維持する。

- 読み取り確認を先に行い、write/deleteは具体的な対象と影響を示して承認を得る。
- 失敗後のretryは、同じdeployの続きとして扱わず、原因と新しい差分を提示して再承認を得る。
- user password、JWT、access key、capability URLをログやrepositoryへ残さない。

### 3.9 実ユーザー検証では観測可能性を先に設計する

現在のLambdaは未処理例外だけを記録し、HTTP API access logも無効である。このため、正常な403、route、JWT subjectをCloudWatch Logsだけでは証明できない。

今後、本番相当の検証が必要なら次を検討する。

- Authorization header、JWT、email、request bodyを含めないHTTP API access logを短期保持で有効化する。
- status、route、request IDだけを記録する。
- 所有者認可はブラウザーのstatusと、DynamoDBの強整合read前後で確認する。

## 4. 良かった点

- build、unit test、E2E、synth、secret scanを各修正後に繰り返した。
- `cdk diff --no-change-set`でAWSを変更せずに差分を確認した。
- 失敗時にCloudFormation event、残存resource、S3 object数を確認してから復旧した。
- S3 public access block、OAC、CORS、JWT route、Budget、ログ保持を実AWSで確認した。
- テストユーザーのpasswordやtokenを共有せず、Cognito statusとDynamoDB GSIから結果を確認した。
- 設計判断と運用状態を`AGENT_INDEX.md`、`README.md`、`context.md`へ同期した。

## 5. 保留事項

デモ成立には影響しないため、次は未実施のまま開発を完了する。

- 別所有者によるDELETEが403になる実ユーザー検証
- プライマリ配信を意図的に失敗させる実環境フォールバック検証
- 検証用DynamoDB itemの整理
- ハッカソン後の削除日と担当者の確定
- アプリstack削除後にCDK bootstrap resourceも削除するかの判断

削除操作は、対象データと影響を再確認し、明示承認を得てから行う。
